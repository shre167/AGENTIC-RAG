### BM25 implementation

- Class: `BM25Retriever` in `src/bm25_retriever.py`
- Called via `bm25.query(search_text, top_k=retrieval_k)` in `retrieval.py:bm25_retrieve()`
- Returns a list of dicts with `chunk_id`, `filename`, `text`, `bm25_score` and canonical metadata fields
- `retrieval_k = min(max(BM25_TOP_K, RERANK_CANDIDATE_LIMIT), MAX_RERANK_CANDIDATES)` = `min(max(10, 20), 30)` = 20

### Dense implementation

- Via `UnifiedVectorStore` → Chroma `collection.query(embedding, n_results=retrieval_k)`
- `dense_retrieve` returns `dict[str, Candidate]` keyed by `filename::chunk-{chunk_id}`
- Distance is raw Chroma cosine distance (lower = better)

### Hybrid and RRF

- Hybrid: dense + BM25 run concurrently in `execute_retrieval_attempt` via `ThreadPoolExecutor`
- `fuse_rrf(candidates, rrf_k=60)` — formula: `RRF(d) = 1/(60 + dense_rank) + 1/(60 + bm25_rank)`
- Page-match bonus: `+0.05` added to RRF score for `is_page_match` candidates
- Result is sorted descending by `(rrf_score, in_both_retrievers)`, capped at `RERANK_CANDIDATE_LIMIT=20`

### Evidence evaluation (`evidence.py`)

Three separate code paths keyed on mode:

**Hybrid:**
1. Check RRF floor: `top_score >= RRF_ABSTAIN_FLOOR` (0.008). Fail → level="none".
2. Check direct/lexical support on top candidate. Fail → level="weak", no answer.
3. Strong: `page_supported OR (agreement AND top_score >= STRONG_RRF_THRESHOLD(0.022) AND (lexical OR direct))`
4. Moderate: `page_supported OR (top_score >= 0.008 AND (lexical OR direct OR agreement))`
5. Weak → no answer.

**Vector:**
1. `_dense_score()`: computes separation between top-1 and top-2 distances.
2. Strong: `dense_rank==1 AND separation>=0.5 AND direct_support`
3. Moderate: `dense_rank<=3 AND (direct OR separation>=0.25)`
4. Not moderate → weak, no answer.

**BM25:**
1. Find `supported` candidates (lexical/direct support).
2. Strong: `best_supported.bm25_rank==1 AND lexical_support`
3. Moderate: `best_supported.bm25_rank<=5`
4. Not moderate → weak, no answer.

### Context selection

`select_context_candidates` in `context.py`:
- Sorts by mode-appropriate key (RRF / dense rank / BM25 rank)
- Deduplicates by key + normalized text
- Limits to `MAX_CHUNKS_PER_SOURCE=3` per filename
- Caps at `MAX_CONTEXT_CHUNKS=10` total
- Hard character cap: `MAX_CONTEXT_CHARS=18000`

### Citations and confidence

- `generate_claim_citations` in `citations.py`: splits LLM answer into claims, lexical-matches each claim against context chunks, assigns `[N]` markers
- `evaluate_confidence` in `confidence.py`: uses `EvaluationResult` + citation coverage + evidence level → `HIGH/MEDIUM/LOW` with score 0-100

### Tracing and observability

- Every query populates a `trace` dict inside `_answer_question_impl`; keys: `query`, `retrieval`, `evidence_gate`, `evaluation`, `citations`, `grounding`, `confidence`, `context`, `generation`, `candidate_journey`, `token_optimizer`
- `observe_pipeline_answer` (observability.py) emits Langfuse trace if enabled
- `record_observation` (observation_store.py) appends a JSON record to `vectorstore/observations.json`
- `build_observatory_snapshot(trace)` (observatory.py) reshapes the trace dict for the Retrieval Lab UI
- `agent_activity` dict is placed inside the response at top level and inside `trace["agent_activity"]`, but **is not yet rendered in the Streamlit UI** — no `_render_agent_activity()` function exists in `app.py`

### Key field name mappings to know for filters

| Semantic need | Correct Chroma field | Notes |
|--------------|---------------------|-------|
| Document name | `filename` | Use this for book-level filters |
| Book title (display) | `book_title` | Redundant with `filename`; always set |

### Reliability of `page_number` and `chapter_num`

- `page_start`/`page_end` are **always written** (defaulting to 0 if unknown). For PDFs, page numbers are extracted per page during loading and are reliable for well-formed PDFs. For TXT/MD files, page numbers default to 0 since there are no physical pages.
- `chapter_num` is **always written** (defaulting to 0). Chapter detection depends on heading patterns in the document loader. It is reliable for books with standard "Chapter N" headings, unreliable for academic papers or docs without clear chapter structure.
- **Neither field is None** — they default to 0, so filter code must test `> 0` not `is not None`.

## D. Existing Evidence Evaluation Logic

### How evidence is scored

Evidence scoring is in `evidence.py: evaluate_evidence(candidates, reranked, search_text, retrieval_mode)`.

**Key thresholds** (from `src/rag_pipeline/config.py`):

| Constant | Value | Meaning |
|---------|-------|---------|
| `RRF_ABSTAIN_FLOOR` | 0.008 | Minimum RRF score to not immediately abstain |
| `STRONG_RRF_THRESHOLD` | 0.022 | RRF score needed for "strong" evidence |
| `MODERATE_RRF_THRESHOLD` | 0.008 | Alias for floor |

**What "sufficient" means:**  
`evidence.should_answer == True` AND `final_candidates` is non-empty.  
The controller additionally checks `sufficient = bool(evidence.should_answer and final_candidates)`.

**`_has_direct_text_support(candidate, query_tokens)`:**  
Returns True if:
- `is_page_match` flag is set, OR
- lexical overlap > 0 (any query token appears in chunk text), OR  
- Any 3+ char query token appears as substring in chunk text (including stem check)

This is the most permissive check — even a single query term match in the chunk text counts.

**`_has_lexical_support(candidate, query_tokens)`:**  
Returns True only if `bm25_score > 0` AND `_has_direct_text_support`.

### Reliability issues in evidence evaluation

1. **`_has_direct_text_support` is overly permissive for Vector mode.** The stem/substring fallback (`token[:-1] in text_lower if token.endswith("s")`) is applied globally, not only for plural forms. A chunk about "telescopes" would match a query about "telescope" even with zero lexical BM25 score.

2. **The Vector-mode "strong" threshold is fragile.** `_dense_score()` computes separation between the top-1 and top-2 distances. If only one candidate is retrieved, `separation=0.0`, making strong evidence impossible regardless of how good the match is. This is a real edge case but rare.

3. **`chapter_num == 0` means front matter, not "no chapter."** Filter code that does `where = {"chapter_num": {"$eq": chapter_num}}` in `chapter_retrieve` will correctly match chapter 0 as front matter, but most callers expect chapter 1+. The guard `if chapter_num < 1: return None` in `extract_chapter_query_info` prevents chapter 0 requests from user queries — this is correct.

4. **`page_start == 0` means "unknown page" in TXT/MD files.** The `page_retrieve` function calls `vector_store.get_chunks_by_page(page_start=0, ...)` which would return all TXT/MD chunks since they all have `page_start=0`. This is a real bug: requesting page 0 from a user would retrieve all TXT chunks. The guard in `extract_page_query_info` (`return None` when no page pattern matches) protects against this in practice, but a malicious/malformed `page_start=0` passed directly to `page_retrieve` would produce wrong results.

5. **RRF score is not a probability.** With `k=60`, a rank-1 result in both retrievers scores `1/61 + 1/61 ≈ 0.0328`, well above `STRONG_RRF_THRESHOLD=0.022`. A rank-1 in one retriever scores `1/61 ≈ 0.0164`, above `RRF_ABSTAIN_FLOOR=0.008` but below `STRONG_RRF_THRESHOLD`. This means most hybrid queries that get a top-1 in only one retriever land at "moderate" evidence, which is correct behavior.

## E. Identified Bugs and Reliability Issues

### E.1 — `agent_activity` is produced but NOT rendered in the Streamlit UI

**File:** `app.py` — there is no `_render_agent_activity` function, no "Agent Activity" expander, no display of `question_type`, `retrieval_plan`, `attempts`, or `final_decision`.

The `agent_activity` dict is present in the response at `response["agent_activity"]` and in `response["trace"]["agent_activity"]`, but `_build_meta()` (app.py L≈723) does not extract it, and `_render_answer_extras()` never renders it.

**Impact:** The entire controller's decision log is invisible to the user. This is the primary missing feature requested.

### E.2 — `_build_meta()` does not extract `agent_activity`

**File:** `app.py`, function `_build_meta` (L≈723). It reads `trace`, `snapshot`, `evidence`, `retrieval`, etc. but has no key for `agent_activity`. The meta dict passed to `_render_answer_extras` never includes agent activity.

### E.3 — `page_retrieve` depends on `vector_store.get_chunks_by_page` ✅ VERIFIED EXISTS

**File:** `src/rag_pipeline/retrieval.py`, function `page_retrieve` (L≈91). The function calls `vector_store.get_chunks_by_page(...)`. **Verified:** `UnifiedVectorStore` in `src/unified_vector_store.py` (L≈60) does implement `get_chunks_by_page` and delegates to `self._backend.get_chunks_by_page`. The backend `ChromaVectorStore` in `src/vector_store.py` also implements it. `BM25Retriever` in `src/bm25_retriever.py` also has it. This is NOT a bug.

**Impact:** None — page retrieval works correctly when the backend supports it.

### E.4 — `chapter_retrieve` uses `{"chapter_num": {"$eq": chapter_num}}` but fallback uses `{"filename": {"$eq": book_title}}`

**File:** `src/rag_pipeline/retrieval.py`, `chapter_retrieve` (L≈146). When `book_title` is provided and no results come back from the `book_title` filter, it retries with `{"filename": {"$eq": book_title}}`. This is correct behavior, but there's a subtle issue: if `book_title` is a display name like `"Deep Work"` but the stored `filename` is `"Deep Work.pdf"`, the retry also fails silently. Both the `book_title` and `filename` stored fields have their exact string value — partial matching is not supported.

**Impact:** Book-specific chapter queries may silently return all-book results (no book filter) if neither `book_title` nor `filename` exactly matches. The `extract_chapter_query_info` function uses `get_book_aliases` which handles this via alias matching, so the `book_match` passed in should be the canonical key. Alias resolution happens **before** `chapter_retrieve` is called, so this is OK if `get_book_aliases` returns the canonical filename as a key.

### E.5 — `section_heading` vs `section_title` naming inconsistency

**File:** `pipeline.py: _build_chunk_metadata` (L≈1280). Both `section_heading` and `section_title` are set to the same value. In `document_loader.py`, chunks only have `section_title`. In `bm25_retrieve` in `retrieval.py`, the `CANONICAL_FIELDS` tuple includes both `section_heading` and `section_title`. The UI in `app.py` checks `chunk.get("section_heading") or chunk.get("section_title")`. This redundancy is harmless but wastes metadata storage.

### E.6 — `prev_chunk_id` and `next_chunk_id` are always empty strings in Chroma

**File:** `pipeline.py: _build_chunk_metadata` writes both as `chunk.get("prev_chunk_id") or ""`, meaning if the document loader set them, they are preserved; if not, they default to `""`. The `chunk_to_chroma_record` function in `document_loader.py` explicitly comments them out. So neighbor-chunk navigation is not functional even though the fields exist.

### E.7 — Double `"retrieval_ms"` and `"llm_ms"` keys in trace dict

**File:** `pipeline.py: _answer_question_impl`, the `trace["retrieval"]` dict (L≈2090) has `"retrieval_ms"` and `"llm_ms"` keys set **twice** in the same dict literal. Python silently uses the last value. This is a code bug, harmless in practice but indicates a copy-paste error.

### E.8 — `MAX_RETRIEVAL_ATTEMPTS = 2` in controller, but first attempt does real retrieval on attempt_index=0 and re-runs rerank on the best result at end

**File:** `controller.py` L≈377. After the loop, if `best` is set and sufficient, `phase.reranked = self.pipeline._rerank(question, fused)` is called again on the already-evaluated candidates. Since `rerank()` always returns `False` (CrossEncoder disabled), this is harmless but redundant.

### E.9 — Multi-intent splitting does not use the controller

**File:** `pipeline.py: _answer_multi_intent` (L≈1367). When `is_multi_intent_query` returns True, the pipeline splits the question and calls `_answer_question_impl` on each sub-question **recursively**, each sub-call goes through the controller individually. The merged result does not carry a unified `agent_activity` dict. The outer `agent_activity` from step 6 is overwritten/missing for multi-intent responses.

### Risk flags for Phase 2

1. **`get_chunks_by_page` on `UnifiedVectorStore`:** Verified present at `src/unified_vector_store.py` L≈60. Delegates to backend `ChromaVectorStore.get_chunks_by_page`. No issues.

2. **Agent activity in chat history JSON:** The `meta` dict is serialized to `vectorstore/chat_history.json` via `_save_persistent_chat_turn`. If `agent_activity` contains non-serializable objects, this will raise on save. The `agent_activity` dict only contains Python primitives (str, int, float, bool, list, dict), so this should be safe.

3. **UI rendering without trace:** If `response.get("agent_activity")` is `{}` or missing (e.g., for greeting responses), `_render_agent_activity` must handle the empty/None case gracefully without crashing.

4. **`section_heading` vs `section_title`:** The `_extract_metadata` function in app.py checks `row.get("section_heading") or ""` first. The `build_context` function stores `section_heading` as `metadata.get("section_heading") or metadata.get("section_title")`. Both fields are written by `_build_chunk_metadata`. No change needed.

5. **`book_title` normalization:** Several places strip `" (1)"` and `.pdf` from book titles for display. When passing `book_match` to `chapter_retrieve`, the value comes from `get_book_aliases` which uses the original filename as the canonical key (e.g., `"Mind Management, Not Time Management (1)"`). The `chapter_retrieve` tries both `book_title` and `filename` fields in Chroma. The stored `book_title` in Chroma is set by `_build_chunk_metadata` as `chunk.get("book_title") or chunk.get("book_name") or Path(filename).stem`. So the canonical key from aliases must match one of these — verify this for each ingested document.
